    3. El modelo de la acción

    Una acción necesita información enviada por el navegador: los parámetros de la URL ([?name=martin&age=42]), los campos de formulario y los parámetros de ruta. El curso original denomina toda esta información el modelo de la acción. Este capítulo muestra cómo [NestJS] se la proporciona a la acción, la convierte al tipo correcto y la valida.

    import { Controller, DefaultValuePipe, Get, ParseIntPipe, Query } from '@nestjs/common';

@Controller('parameters')
export class ParametersController {
  // /parameters/action01?name=martin
  @Get('action01')
  action01(@Query('name') name: string): string {
    return `name = [${name}], of type ${typeof name}`;
  }

  // /parameters/action02?age=42: un parámetro es SIEMPRE una cadena
  @Get('action02')
  action02(@Query('age') age: number): string {
    return `age = [${age}], of type ${typeof age}`;
  }

  // /parameters/action03?age=42: ParseIntPipe convierte (o rechaza)
  @Get('action03')
  action03(@Query('age', ParseIntPipe) age: number): string {
    return `age = [${age}], of type ${typeof age}`;
  }

  // /parameters/action04?page=2: un valor por defecto si falta el parámetro
  @Get('action04')
  action04(@Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number): string {
    return `page = [${page}], of type ${typeof page}`;
  }

  // /parameters/action05?name=martin&age=42: todos los parámetros a la vez
  @Get('action05')
  action05(@Query() parameters: Record<string, string>): object {
    return parameters;
  }
}

    Analicemos este código:

    • líneas 6–9: [@Query('name')] inyecta el valor del parámetro [name] de la URL (la parte que sigue a [?], llamada cadena de consulta o [query string]);
    • líneas 12–15: el parámetro [age] se declara de tipo [number]... pero este tipo es solo una declaración [TypeScript], que se elimina durante la compilación. Lo que recibimos es siempre una cadena, como lo muestra la ejecución;
    • líneas 18–21: [ParseIntPipe] es un pipe: un objeto que transforma (y valida) el valor de un parámetro antes de que llegue a la acción. Aquí, la cadena ['42'] se convierte en el número 42; una cadena no numérica provoca un error 400 (Bad Request), sin que se ejecute la acción;
    • líneas 24–27: los pipes se encadenan: [DefaultValuePipe(1)] reemplaza un parámetro ausente por 1 y luego [ParseIntPipe] lo convierte;
    • líneas 30–33: [@Query()], sin argumentos, inyecta un objeto que contiene todos los parámetros de la URL.

    3.2. Ejemplo 08: un modelo de acción descrito por una clase

    Cuando una acción tiene varios parámetros, se describen mediante una clase, a menudo llamada [DTO] ([Data Transfer Object]).     import { Type } from 'class-transformer';
import { IsEmail, IsIn, IsInt, IsNotEmpty, IsOptional, Length, Max, Min } from 'class-validator';

export class PersonDto {
  @IsNotEmpty({ message: 'the name is required' })
  @Length(2, 20, { message: 'the name must have 2 to 20 characters' })
  name: string;

  @Type(() => Number)
  @IsInt({ message: 'the age must be an integer' })
  @Min(0, { message: 'the age must be positive' })
  @Max(150, { message: 'the age cannot exceed 150' })
  age: number;

  @IsIn(['Mr', 'Mme', 'Melle'], { message: 'unknown title' })
  title: string;

  @IsOptional()
  @IsEmail({}, { message: 'invalid email address' })
  email?: string;
}

    Analicemos este código:

    • línea 1: [@Type] proviene de la biblioteca [class-transformer], que convierte los datos recibidos;
    • línea 2: los decoradores de validación de [class-validator];
    • líneas 5–7: el nombre es obligatorio ([@IsNotEmpty]) y debe tener entre 2 y 20 caracteres ([@Length]). Cada decorador acepta un mensaje de error personalizado;
    • líneas 9–13: [@Type(() => Number)] exige que la cadena recibida se convierta en número antes de la validación: un entero ([@IsInt]) entre 0 y 150 ([@Min], [@Max]);
    • líneas 15–16: el título debe ser uno de los valores de una lista;
    • líneas 18–20: la dirección de correo electrónico es opcional ([@IsOptional]); si está presente, debe ser válida ([@IsEmail]).

    import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  // validación automática de TODOS los modelos de acción descritos por una clase
  app.useGlobalPipes(
    new ValidationPipe({
      transform: true, // convierte las cadenas recibidas a los tipos declarados
      whitelist: true, // elimina los campos no declarados en la clase
    }),
  );
  await app.listen(3000);
  console.log('Server started on http://localhost:3000');
}

    import { Controller, Get, Query } from '@nestjs/common';
import { plainToInstance } from 'class-transformer';
import { validate } from 'class-validator';
import { PersonDto } from './person.dto';

@Controller('persons')
export class PersonsController {
  // aquí no hay ValidationPipe: la acción recibe los parámetros EN BRUTO y
  // decide por sí misma qué hacer con los errores
  @Get('action01')
  async action01(@Query() raw: Record<string, string>): Promise<string> {
    // 1. objeto en bruto -> instancia de PersonDto (conversiones de @Type incluidas)
    const person = plainToInstance(PersonDto, raw);
    // 2. verificación de las restricciones (@IsNotEmpty, @Min...)
    const errors = await validate(person);
    // 3. una página HTML en ambos casos: sin error 400
    if (errors.length === 0) {
      return `<p>Welcome ${person.title} ${person.name} (${person.age} years old)</p>`;
    }
    const items = errors
      .map((e) => `<li>${e.property}: ${Object.values(e.constraints ?? {}).join(', ')}</li>`)
      .join('');
    return `<p>The form contains errors:</p><ul>${items}</ul>`;
  }
}

    Comentemos este código:

    • línea 11: la acción recibe los parámetros sin procesar: un objeto cuyos campos son todos cadenas;
    • línea 13: [plainToInstance] ([class-transformer]) crea una instancia de [PersonDto] a partir del objeto sin procesar, aplicando las conversiones ([@Type]);
    • línea 15: [validate] ([class-validator]) verifica todas las restricciones. Devuelve un arreglo de errores, que está vacío si todo está bien. Cada error indica el campo problemático ([property]) y los mensajes de las restricciones infringidas ([constraints]);
    • líneas 17–18: sin errores, una página de bienvenida;
    • líneas 20–23: en caso contrario, una página que enumera los errores. En ambos casos, la respuesta es una página HTML, con código de estado 200.

    Esta es la técnica que usarán todos los formularios del caso de estudio (véase el ejemplo 19).

import { ArrayMinSize, IsArray, IsIn } from 'class-validator';

export class ChoiceDto {

    import { BadRequestException, Injectable, PipeTransform } from '@nestjs/common';

// convierte una fecha francesa "23/09/2026" en una fecha ISO "2026-09-23"
@Injectable()
export class DateFrPipe implements PipeTransform<string, string> {
  transform(value: string): string {
    const m = /^(\d{2})\/(\d{2})\/(\d{4})$/.exec(value ?? '');
    if (!m) {
      throw new BadRequestException(`[${value}] is not a date in the dd/mm/yyyy format`);
    }
    const [, day, month, year] = m;
    const iso = `${year}-${month}-${day}`;
    // "31/02/2026" tiene el formato correcto, pero no existe
    if (new Date(`${iso}T00:00:00Z`).toISOString().slice(0, 10) !== iso) {
      throw new BadRequestException(`the date [${value}] does not exist`);
    }
    return iso;
  }
}
    • líneas 4–5: un pipe es una clase [@Injectable()] que implementa la interfaz [PipeTransform<input, output>];
    • línea 6: su método [transform] recibe el valor del parámetro y devuelve el valor transformado, que recibirá la acción;
    • líneas 7–9: un valor que no tiene la forma [dd/mm/yyyy] provoca una [BadRequestException] (400);
    • líneas 13–15: una fecha que tiene el formato correcto pero no existe (31/02/2026) también se rechaza: [new Date] la “corrige” a 03/03/2026, lo cual se detecta.

    import { createParamDecorator, ExecutionContext } from '@nestjs/common';
import { Request } from 'express';

// @Language(): el idioma preferido del navegador, leído del encabezado
// "Accept-Language: fr-FR,fr;q=0.9,en;q=0.8" -> "fr"
export const Language = createParamDecorator((fallback: string | undefined, ctx: ExecutionContext): string => {
  const req = ctx.switchToHttp().getRequest<Request>();
  const header = req.get('accept-language') ?? '';
  const first = header.split(',')[0].trim().slice(0, 2).toLowerCase();
  return first || fallback || 'fr';
});
    • Línea 6: [createParamDecorator] crea un decorador de parámetro, similar a [@Query] o [@Body]. La función recibe el argumento del decorador ([@Language('fr')]) y el contexto de ejecución de la consulta;
    • línea 7: el contexto da acceso a la solicitud [Express];
    • líneas 8–10: se devuelven las dos primeras letras del encabezado [Accept-Language], que indica los idiomas preferidos del usuario.

    import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(
    new ValidationPipe({
      transform: true,
      whitelist: true, // los campos no declarados se eliminan...

  await app.listen(3000);
  console.log('Server started on http://localhost:3000');
}

    3.6.4. Conclusión

    El modelo de la acción es generado por [NestJS] a partir de la solicitud: parámetros de ruta ([@Param]), URL ([@Query]), cuerpo ([@Body]) y encabezados ([@Headers]). Los pipes convierten y validan estos valores. Para una aplicación HTML, normalmente es preferible validar el modelo uno mismo (ejemplo 09) para poder volver a mostrar el formulario.
